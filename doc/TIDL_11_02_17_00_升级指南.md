## 2. 设备端要更新的东西（精确清单）

### 2.1 C7x DSP 固件 — **只有 2 个文件**

`update_target.sh` 从 `firmware.tar.gz` 里 **只取匹配 `*c7*.out*` 的文件**（`cd firmware/ti-ipc/am62axx && find ./ -name "*c7*.out*"`）。
tarball 里虽然打包了整个 `/lib/firmware`（含 iwlwifi、ti-connectivity、tee.bin 等无关内容），**这些一律不动**。

| 文件 | 大小 | md5 |
|---|---|---|
| `dsp_edgeai_c7x_1_release_strip.out` | 11145240 | `ddfc1e414ba8b7f6e3bc1603b7ceb148` |
| `dsp_edgeai_c7x_1_release_strip.out.signed` | 11146921 | `f109b8acf5242d0f6e171b8f97001f61` |

**官方脚本的目标路径（AM62A 分支）**：
```
/lib/firmware/ti-ipc/am62axx/
```
> ⚠️ **不是** `/lib/firmware/vision_apps_evm/` —— 那是 J721E/J721S2/J784S4 的路径。

### 🔴🔴 Mo 62A 致命坑：官方脚本刷的位置**不是**设备实际加载的位置

**2026-08-17 设备实测（10.5.30.132，V1.0.9）**：

```
$ cat /sys/class/remoteproc/remoteproc0/{name,firmware}
7e000000.dsp
am62a-c71_0-fw

$ ls -l /lib/firmware/am62a-c71_0-fw
/lib/firmware/am62a-c71_0-fw -> /opt/ti/firmware/am62a-c71_0-fw     ← 指向第三个位置！

$ ls -l /opt/ti/firmware/am62a-c71_0-fw
-rw-rw-r-- 1 debian debian 19329752  5月 30 12:13               ← 19.3 MB，11.01 时代
```

而 11_02_17_00 的新固件是 **11.1 MB**（11145240 B）。

> **⇒ `update_target.sh` 在 Mo 62A 上刷固件是【静默无效】的**：
> 它写 `/lib/firmware/ti-ipc/am62axx/`，而 remoteproc 加载的是 `/opt/ti/firmware/am62a-c71_0-fw`。
> 脚本不报错、不生效，事后 `md5sum` 那个路径还"看起来对了"——极具欺骗性。

**正确做法**：三个位置都要处理，并以 remoteproc 实际加载的那个为准。

```bash
# 1. 查清 remoteproc 到底加载哪个文件（唯一权威）
for r in /sys/class/remoteproc/remoteproc*; do
  echo "$r: $(cat $r/name) fw=$(cat $r/firmware) state=$(cat $r/state)"
done
# 2. 顺着 symlink 找到真身
readlink -f /lib/firmware/am62a-c71_0-fw
# 3. 备份后替换【真身】
sudo cp /opt/ti/firmware/am62a-c71_0-fw{,.bkp-v109}
sudo cp .../dsp_edgeai_c7x_1_release_strip.out /opt/ti/firmware/am62a-c71_0-fw
# 4. 同时也更新官方路径，保持一致（避免以后混淆）
sudo cp .../dsp_edgeai_c7x_1_release_strip.out{,.signed} /lib/firmware/ti-ipc/am62axx/
# 5. 重启后核验【真身】的 md5
md5sum $(readlink -f /lib/firmware/am62a-c71_0-fw)   # 期望 ddfc1e414ba8b7f6e3bc1603b7ceb148
```

> ⚠️ 版本字符串**不可用于判版**：新旧固件里都含 `11_01_00_05`（构建期 SDK 引用）。
> **只认 size + md5。**

## 3. 升级后**必须重做**的事

| 对象 | 为什么 | 怎么做 |
|---|---|---|
| **全部模型 artifacts** | 旧 artifacts 由旧工具链编译，新 C7x 固件读不了（实测：旧 artifacts + 新固件 → `vxGetStatus: Reference is NULL`） | 见 §3.1 |
| **C++ `app_edgeai`** | ORT 1.15→1.23，符号版本 `VERS_1.15.0` → `VERS_1.23.0`，**换 .so 救不了** | 见 §3.2 |
| **`edgeai_dl_inferer` python 适配** | ORT 1.23 行为变化 | 见 §4 |

### 3.1 重编 artifacts 的四条铁律（2026-08-17 全量实测，9/9 通过）

**① 必须沿用 TI 自己的 `runtime_options`，不要自拍参数**

每个模型目录下的 **`config.yaml` 里存着 TI 当初编译时的完整参数**，直接读它：

```python
cfg = yaml.safe_load(open(f"{model_dir}/config.yaml"))
ro  = cfg["session"]["runtime_options"]      # ← 原样沿用，只改路径类参数
```

自拍参数的后果（实测对比）：

| 参数 | 自拍 | TI 原始 | 影响 |
|---|---|---|---|
| `advanced_options:output_feature_16bit_names_list` | 无 | **有**（检测头关键层 16bit 混合精度） | 缺了 → human-pose/robokit **编译失败**（3~6 个 TIDLRT 错误） |
| `advanced_options:quantization_scale_type` | 默认 | **4**（QAT 的 robokit 是 **1**） | 影响量化正确性 |
| `activation_clipping`/`weight_clipping`/`bias_calibration` | 无 | 全 1 | 精度 |
| `calibration_frames` / `calibration_iterations` | 8 / 3 | **12 / 12** | 帧数必须与实际喂入一致 |
| `input_optimization` | 自动判断 | **每模型不同**（有 true 有 false） | false 的要按 `input_mean`/`input_scale` 手工归一化 |

**② 路径类参数必须重映射到本地**

TI 的 `config.yaml` 里记的是他们内部机器的绝对路径（`/home/tensorlab-test/...`）：

| 参数 | 处理 |
|---|---|
| `object_detection:meta_layers_names_list` | 指向本地 `model/*.prototxt`（排除 `*_qparams.prototxt`） |
| `advanced_options:quant_params_proto_path` | 指向本地 `model/*_qparams.prototxt` |
| `tidl_tools_path` / `artifacts_folder` | 换成本地路径 |
| `platform` / `version` / `import` / `model_path` | 丢弃 |

> 检测模型漏传 `meta_arch_type` + `meta_layers_names_list` → `Populate OnnxRT Output Params Failed`。
> 类型对照（`docs/od_meta_arch.md`）：TfLite SSD=1、ONNX SSD=3、YOLOv3=4、RetinaNet/EfficientDet=5、
> **YOLO-X/v5/v7=6**、Pointpillars=7、**YOLO-V8=8**。

**③ 部分 `qparams.prototxt` 是旧格式，11.02 解析器不认**

```
[TIDL Import] [QUANTIZATION] ERROR: Reading prototext file failed
Error parsing text-format TIDLNetQuantParams: 12:19: Expected string, got: 0
```
这类模型（实测 `fpnlite-aspp`）**直接不传** `quant_params_proto_path` 即可。

**④ 触发 AM62A 特有算子限制的模型，先跑 `tidl_onnx_model_optimizer`**

实测 `fpnlite-aspp` 报 `Conv | Padding greater than input width is not supported for AM62A and AM67A`：

```python
from tidl_onnx_model_optimizer import optimize
optimize(src_onnx, opt_onnx)        # 默认规则集即可，含 convert_conv_large_pad_to_smaller_kernel
```
结果：211 → 207 节点，**207/207 全 offload，19.49 ms**。

> ⚠️ **优化器改了模型结构，设备上的 `.onnx` 必须一并替换**，否则 artifacts 与模型对不上。

### 3.2 C++ `app_edgeai` 重编要点

除了重新编译，还要换掉 **4 处**旧依赖（都来自 base rootfs / 仓库里的旧版本）：

| # | 对象 | 从哪来 | 换成 |
|---|---|---|---|
| 1 | `include/onnxruntime/` + `include/core/` | 仓库（ORT **1.15** 头，`ORT_API_VERSION 15`） | ORT 1.23 源码的 `include/onnxruntime/`（`ORT_API_VERSION 23`） |
| 2 | `include/*.h`（平铺的 ORT 头） | 同上 | **ORT 1.23 把 C API 拆成了多个头**（新增 `onnxruntime_ep_c_api.h`、`onnxruntime_float16.h` 等），必须把 `core/session/*.h` 全部平铺过去 |
| 3 | `prebuilt/tflite/*.a` | 旧构建 | 新 tflite 静态库（79 个） |
| 4 | chroot 内 `/opt/ti/edgeai/lib/lib{onnxruntime,tivision_apps}.so` | **base rootfs 里的旧版** | 11_02_17_00 的版本 |

第 4 项最隐蔽：`build.sh` 从 base tar 解出的 chroot 里取 TI 运行时库，那是**镜像发布时的版本**。
已在 `build.sh` 加了 `TIDL_LIB_OVERRIDE`（默认读 `prebuilt/ti-lib/`）来覆盖。

**已知会踩的编译错误**：
```
core/providers/tidl/tidl_provider_factory.h: No such file    → include/core/ 只拷了 session/，要拷整个 core/
onnxruntime_ep_c_api.h: No such file                        → ORT 1.23 拆头，平铺补齐 core/session/*.h
```

## 4. ORT 1.23 带来的两处必改（否则必挂）

### 4.1 关闭 IO 校验
ORT 1.23 对 TIDL EP 的张量做严格校验，报 `GetElementType is not implemented`。

```python
so = onnxruntime.SessionOptions()
so.add_session_config_entry("session.disable_input_validation", "1")
so.add_session_config_entry("session.disable_output_validation", "1")
```

### 4.2 关闭 ORT 图优化，且**编译端与推理端必须一致**
依据 `docs/debugging.md` 第 6 条。

```python
so.graph_optimization_level = onnxruntime.GraphOptimizationLevel.ORT_DISABLE_ALL
```

| 编译端 | 推理端 | 结果 |
|---|---|---|
| DISABLE_ALL | DISABLE_ALL | ✅ 正确 |
| DISABLE_ALL | 默认 | ❌ **段错误 rc=139** |
| 默认 | 任意 | ❌ ORT 先改图 → TIDL 只能切多子图 + TIDLRT 报错 |

设备端需 patch：`/usr/local/lib/python3.*/dist-packages/edgeai_dl_inferer/__init__.py`（改前备份）。

## 5. ⚠️ Mo 62A 特有问题：Python 版本不匹配 —— **已自建 cp313 解决**

| | TI 官方前提 | Mo 62A 实际 |
|---|---|---|
| 根文件系统 | Arago (Yocto) | **Debian 13.5 (trixie)** |
| Python | 3.12（官方 wheel 全是 `cp312`） | **3.13.5** |
| 库路径 | `/usr/lib` | `/opt/ti/edgeai/lib`（+ `/usr/lib`） |
| site-packages | `/usr/lib/python3.12/site-packages` | `/usr/local/lib/python3.13/dist-packages` |

**根本原因**：Python 3.13 移除了 `_PyThreadState_UncheckedGet` 符号，cp312 编的
`onnxruntime_pybind11_state.so` 在 3.13 下 import 直接报 `undefined symbol`。
官方 **cp313 wheel 不存在**（实测 HTTP 404）。

### 5.2 已验证的事实

**ORT wheel**（`readelf` / `strings` 实测）：
- ✅ 版本 **1.23.0**，与 11_02_17_00 要求一致
- ✅ 含 TIDL EP 符号：`TIDLExecutionProvider`、`TIDLCompilationProvider`、
  `onnxruntime::TidlExecutionProvider::GetCapability(...)`、`tidl_tools_path`
- ✅ 符号版本 **`VERS_1.23.0`** ← 这正是 C++ `app_edgeai` 必须重编的原因（旧的链的是 `VERS_1.15.0`）
- ✅ 包内含 `libonnxruntime.so.1.23.0` + `onnxruntime_pybind11_state.so`(cp313)

**TFLite wheel**：
- ✅ `_pywrap_tensorflow_interpreter_wrapper.cpython-313-aarch64-linux-gnu.so` → cp313 正确
- ✅ `interpreter.py` 含 `load_delegate` / `experimental_delegates` → 能挂 `libtidl_tfl_delegate.so`
- ⚠️ 版本是 **2.12.1**，TI 脚本写的是 **2.12.0**。delegate 走 `TfLiteDelegate` C API，2.12.x 内 ABI 稳定，

### 5.4 结论

**§2.3 的 OSRT 部分不再是阻塞项。** 不要跑官方 `update_target.sh` 的 OSRT 分支

```bash
export UPDATE_OSRT_COMPONENTS=0
export UPDATE_FIRMWARE_AND_LIB=1
```
OSRT 用上面自建的 cp313 wheel **手工安装**。

## 10. 板端验证方案（11_02_04_00+ 新特性）

11_02_04_00 是一次**重大更新**，核心是让 TIDL 更容易吃下原生模型。四层验证：

| 层 | 测什么 | 判据 |
|---|---|---|
| **L0 回归** | `yolox-nano-lite` | 必须仍 ~11.7ms / 283 全 offload。**升级后第一件事**，挂了说明升级本身有问题 |
| **L1 算子级** | 板端跑 `test/tidl_unit` pytest | 与官方 `test/reports/Operator_Test_Report_AM62A_8bits.xlsx` 逐项对比。TI 提供了同款 SoC 的官方逐算子基准，差异即我们环境问题 |
| **L2 新特性** | DeiT-tiny / SWIN（`docs/vision_transformers.md` 声明已支持） | 上一轮 10 个 TIDLRT 错误；固件正确后重测 |
| **L3 原生模型** | 标准 YOLO11，**不做任何手工改**，只过一遍 `optimize()` | 检验"TI 是否真支持原生模型"的关键实验 |

### L1 命令 —— ⚠️ Mo 62A 上必须加两个参数

```bash
cd /opt/edgeai-tidl-tools/test/tidl_unit
sudo -E env SOC=am62a LD_LIBRARY_PATH=/opt/ti/edgeai/lib \
  python3 -m pytest test_tidl_unit.py \
    --configs ../../runtimes/examples/python/basic_example/config.yaml \
    --run-infer -n 1 \
    --timeout 240 \        # ← 必须：aarch64 默认只有 10 秒，不够
    --no-subprocess        # ← 必须：Python 3.13 下不加必然死锁
```

| 参数 | 不加会怎样 | 原因 |
|---|---|---|
| **`--no-subprocess`** | 每个模型都 `PROCESS TIMED OUT`，加大 `--timeout` 也没用 | 框架默认 `os.fork()` 起子进程，而主进程加载 TIDL 后已是多线程 → **fork 后子进程死锁**。Python 3.13 会打 `DeprecationWarning: This process is multi-threaded, use of fork() may lead to deadlocks`。TI 按 Arago 的 **py3.12** 开发，不触发此问题 |
| **`--timeout <秒>`** | 10 秒就被杀，模型其实加载正常 | README 明写 aarch64 默认 10s |

> 这两条 TI 文档里没有，是 **Debian 13 / Python 3.13 特有**的。
> 实测：加上 `--no-subprocess` 后 3 个 ONNX 模型立刻全部 PASSED（41 秒）。

## 9. 已知能力边界（升级后仍然存在）

11_02_17_00 **不会**让 AM62A 支持标准 YOLO11。这是**产品分级**，不是版本问题：

| | AM62A | AM68A (J721S2) |
|---|---|---|
| L2MEMSIZE_KB | 224 | 448 |
| MSMCSIZE_KB | 1024 | 3872 |
| MATPANELSIZE | **32** | （无此约束） |

同一个 YOLO11 ONNX：AM68A → 328 节点 / 1 子图 / 0 CPU；AM62A → 242 / 3 / 4，且编译器明确拒绝
`MaxPool 5×5 stride=1`（SPPF）和 `Softmax` 轴向（DFL 头），C7x 侧 `TIDL_BatchNormLayer`（SiLU）`algInit failed status=6`。

TI 官方模型全叫 "**lite**"，就是因为把 SiLU 换成了 ReLU **并重新训练**。
仅做算子替换而不重训 → 模型能跑但**输出全 0，检测不出任何东西**（已实测）。

详见 `~/Desktop/yolo-eval/YOLO11_AM62A_编译流程.md`。
