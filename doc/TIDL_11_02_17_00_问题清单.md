## 问题 1 —— AM62A 的 **8-bit 超越函数算子全部失效**（TI 自己的报告即可佐证）

`test/reports/Operator_Test_Report_AM62A_8bits.xlsx` 的 Summary 页显示，下列算子
**板端通过率为 0**，而同一版本的 **AM68A(J721S2) 全部 100% 通过**：

| 算子 | AM62A 8bit | AM62A 16bit | AM68A 8bit |
|---|---|---|---|
| **Sigmoid** | **0/22** | 22/22 | 22/22 |
| **LeakyRelu** | **0/32** | 32/32 | 32/32 |
| **Mish** | **0/22** | 22/22 | 22/22 |
| **Exp** | **0/22** | 22/22 | 22/22 |
| **Log** | **0/22** | 22/22 | 18/22 |
| **Tan** | **0/22** | 8/22 | — |
| **Acos / Asin / Asinh** | **0/22** each | 22/22 | 22/22 |
| Div | 429/880 (48.8%) | 816/880 (92.7%) | 623/880 |

受影响的全部是**超越函数**（指数/对数/三角/Sigmoid 族），且 **16-bit 下同样的算子全部正常** ——
指向 AM62A C7x 固件中 8-bit 超越函数近似/查找表实现的缺陷。

### 实际后果：标准 YOLO11 无法运行

SiLU = `Sigmoid(x) · x`。YOLO11n 含 78 个 Sigmoid。实测：

```
编译（x86，11_02_17_00 工具链）—— 完全干净：
    TIDLRT_invoke 错误 0，单子图，326/326 全部 offload，不支持算子表为空

设备（正确固件）—— 第 5 层失败：
    netLog: 5 | TIDL_BatchNormLayer | /model.0/act/Mul_output_0   ← 第一个 SiLU
    C7x:  Alg Init for Layer # -    4            ✅
          Alg Init for Layer # -    5            ← 卡死
          WorkloadUnitExec_Init: initFuncPtr Failed
          [tivxAlgiVisionCreate:335] algInit failed with status = 6
          [tivxKernelTIDLCreate:1248] tivxAlgiVisionCreate returned NULL
    ARM: Create state function failed. Return value:-1
```

同一 ONNX 在 AM68A 工具链下：328 节点 / 1 子图 / 0 CPU / 不支持算子表为空。

**已排除**：内存不足（需 15 MB，C7x 堆 112 MB）、编译配置、模型表示差异（两边 netLog 均生成 82 个
`TIDL_BatchNormLayer`）、固件版本错配（已核验）。

## 问题 2 —— **16-bit 推理在设备上完全不可用**（与官方报告矛盾）

官方报告称 AM62A 16-bit 板端通过率 **92.2%**（略高于 8-bit 的 92.1%）。
但实测：**16-bit 模型在设备上连 session 都建不起来**，会无限挂起。

| 模型 | 8-bit | 16-bit |
|---|---|---|
| `yolox-nano-lite 416`（TI 官方模型，8-bit 下 10.93 ms 正常） | ✅ | ❌ **挂起** |
| YOLO11n（SiLU） | ❌ 第 5 层 algInit 失败 | ⚠️ 过了 algInit，挂在首次 invoke |

两套编译参数都试过，行为一致：
- (a) TI 原始 `runtime_options` 仅把 `tensor_bits` 改为 16
- (b) 干净参数：额外去掉 `output_feature_16bit_names_list`、`params_16bit_names_list`、
      `quantization_scale_type`、`mixed_precision_factor`

两者编译均干净（`TIDLRT_invoke` 错误 0、单子图、329/329 offload），设备端表现：

```
[1] 建 session
Final number of subgraphs created are : 1, - Offloaded Nodes - 329, Total Nodes - 329
（无输出，330 秒超时；无错误信息、无 C7x 日志）
```

这使得"用 16-bit 规避问题 1"的方案不可行。

## 问题 4 —— 单元测试框架在 **Python 3.13** 下必然死锁

`test/tidl_unit` 默认为每个模型 `os.fork()` 一个子进程。主进程加载 TIDL 后已是多线程，
fork 后子进程死锁：

```
DeprecationWarning: This process (pid=...) is multi-threaded,
use of fork() may lead to deadlocks in the child.
...
PROCESS TIMED OUT     ← 加大 --timeout 也无效
```

**加 `--no-subprocess` 后立即全部通过**（3 个 ONNX 模型 41 秒）。

TI 的 Arago 根文件系统是 Python 3.12，不触发此问题；Debian 13 是 3.13。
建议框架改用 `spawn` 启动方式，或在 3.12+ 自动回退。

## 问题 5 —— 框架把 SoC 不匹配的模型报为 FAILED 而非 SKIPPED

`config.yaml` 中标有 `soc: j784s4` 的模型（如 `cl-ort-resnet18-v1_4batch`、
`cl-ort-resnet18-v1_low_latency`，均需 `num_cores: 4`）在 AM62A 上：

```
[ERROR] Failed to parse config file config.yaml: 'cl-ort-resnet18-v1_4batch'
  File "test_tidl_unit.py", line 361, in perform_test_oneprocess
    model_name: config_data['models'][model_name]   ← KeyError
```

pytest 已为其生成测试用例，但工作进程按 `soc:` 过滤掉了该条目 → KeyError → 报 FAILED。
应报 SKIPPED。

> 违反它得到的任何结论都不可信 —— 包括本文档中曾据此写下的条目。

## 环境类事项（非 TI 缺陷，但文档未覆盖）

| 事项 | 说明 |
|---|---|
| x86 wheel 的 Python 版本 | `onnxruntime_tidl` 有 cp310/cp312；**`tflite_runtime`/`tvm`/`tidlruntime` 只有 cp310**。编 TFLite/TVM 模型必须用 Python 3.10 |
| aarch64 wheel | 官方只到 **cp312**（Arago）。Debian 13 是 3.13，需自行编译（py3.13 移除了 `_PyThreadState_UncheckedGet`，cp312 的 pybind 无法 import） |
| TVM 编译依赖 | 需额外下载 **ARM GCC 13.2** + **TI CGT C7000 5.0.0**（约 2 GB），且 **onnx 必须 ≤1.15**（`onnx.mapping` 在 1.16 被移除） |
| 单元测试超时 | aarch64 默认 10 秒，必须显式 `--timeout` |
| ORT 1.23 device discovery | 在非 PCI 的 DRM 设备上（如 AM62A 的 DSS 显示控制器）读不到 `device/vendor`，导致 **GPU 枚举整体失败**并打 W 级告警。已本地修复：在 `DetectGpuSysfsPaths()` 中跳过无 `device/vendor` 的 card |
